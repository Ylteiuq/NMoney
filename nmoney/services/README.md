# 账本规则和用例

| 文件 | 负责的问题 |
| --- | --- |
| [budget.py](budget.py) | 确认收入到账状态，合并生活费、补记、平台收入与整月实付，计算借款两种口径下的余额。 |
| [clustering.py](clustering.py) | 计算文本和金额的相似度，供初分、HTTP 账本查询及命令行共用。 |
| [loans.py](loans.py) | 将到账还款匹配到借出本金，按有效流水核算待还余额和结清差额。 |
| [ledger.py](ledger.py) | 导入时按平台和订单号去重、比较快照时间。处理分类、日常选择、单笔上限、群收款抵扣，以及组织概览查询。 |
| [rules.py](rules.py) | 用 `payment_state` 识别资金性质，用 `evaluate` 算出单笔实付、用途及归属，再用 `summarize` 按分类和月份汇总。 |
| [classification.py](classification.py) | 在指定日期范围运行相似支出初分。用同组交易推断未知用途，并用已有手工用途做留一验证。 |

## 在哪里改统计口径

- **实际支付**取 `payment` 为真的流水（已付款，排除理财和内部划转），累计其中已知的 `personal`。分期汇总和明细都按原付款日归属。全额退款实付为零，退款金额未知时为 `None`，单列待核对笔数和原额。原付对账沿用含理财买入的 `outflow`。
- 普通付款的**用途**依次看单笔标注、同平台同名商户规则、商品和平台类别推断。仍然未知且没有人工指定时，才采用模型的 `initial_category`。**日常归属**单独取手工选择，其次取初分。改一笔为「非日常」可以保留它的餐饮用途。
- **群收款**在原付款日抵扣。服务先取跨月、跨平台的关联，再筛选本次要展示的原付款。关联回款和批量日常标记使用 `session(immediate=True)`，在核对现有数据前取得写锁。

## 怎样读初分结果

初分复用 [独立聚类模块](clustering.py)。遇到用途未知的付款，至少有两笔其他相似交易有一致的手工用途或商户规则才采用推断。证据不足就保留未知。已手工决定或已主动退回待确认的日常选择会保留。留一验证逐笔隐藏目标交易自己的手工标签，用其余手工标签预测，再统计能预测几笔、其中吻合几笔。

从项目根目录执行 `python3 -m nmoney.trial --start 2026-11-01 --end 2026-11-23` 可预览统计。指定 `--db` 可选测试账本，显式加 `--apply` 才写入初分结果。

日常偏好只取同平台、同商户和归一化商品说明的人工标记，未知商品的美团团购额外匹配价位。同类出现分歧则保留待确认。医疗、超过个人实付上限和借出本金优先单列。借款结清后仅差额进入日常统计。
